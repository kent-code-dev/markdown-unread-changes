### 確認済み
- 拡張の名前：Markdown Unread Changes。拡張 ID `markdown-unread-changes`、設定のキー `markdownUnreadChanges.*`。Marketplace に同名の拡張がないことは確認済み。似た拡張の Markdown Inbox はファイル単位の既読管理で、ファイル内の変更の色付けはしないので競合しない
- 発行者 ID（publisher）：`kent-code-dev`（「kent」は GitHub や X でも使っている開発用の名前で、意図どおり）
- ライセンス：MIT（MCP サーバのリポジトリと同じ）
- リポジトリ名とフォルダ名：`markdown-unread-changes` にそろえる（コードを書く前に変更する）
- 対応する VS Code の最低バージョン（`engines.vscode`）：`^1.90.0`（使う API はすべて 1.90 以前からある。`@types/vscode` は 1.90.0 に固定し、新しい API を誤って使わないようにする）
- 大前提：インターネットに一切接続しない。ノートの内容・利用状況・エラー情報を外部に送らない。CDN などから実行時にファイルを読み込まない（プレビュー用の CSS/JS もすべて拡張に同梱する）
- 既読の状態は `context.storageUri`（VS Code が管理する、ワークスペースごとのローカルフォルダ）に保存する。保存するのは、既読にした時点の本文のスナップショット
- オフライン前提の確認方法：開発初日から 1（ESLint で禁止）+ 2（依存の制限）+ README の Privacy 節を入れる。公開前に 3（.vsix の検査）+ 4（テストの罠）を CI に追加する（「オフライン前提の確認方法」の節を参照）
- 実行時の依存は原則ゼロ。例外は、通信しないことを確認したパッケージだけ
- 差分の単位：行単位で検出し、ブロック単位（段落・見出し・リスト項目・表の行など）で色を付ける。文字単位は最初の版では見送る（後から追加できる作りにする）
- 差分アルゴリズム：自作する（行単位の Myers 法）。隣り合う削除と追加は「変更（黄色）」として対応づける。行数が同じなら先頭から順に、違うなら似ている行どうし（文字の 2-gram の類似度が 0.5 以上）を順序を保って対応づけ、余った削除は赤、余った追加は緑で表示する（2026-11-17 変更）
- ブロックの途中で消えた行も、黄色に吸収せず赤で表示する。黄色のブロックの「変更前」には、消えた行も含める
- 追跡するファイルの範囲：ワークスペース内の .md をすべて追跡する。初回起動時に全ファイルを「既読」として取り込み、その後の変更はファイルの監視で検知する。除外したいフォルダは設定で指定できる
- 大規模フォルダ対策：`include` / `exclude` / `maxFiles` / `maxFileSize` の設定を設ける。上限を超えたら、全件の取り込みをやめて「開いたファイルだけ追跡するモード」に切り替え、通知で設定を勧める（「大規模フォルダ対策」の節の提案 1〜3。上限の値は仮で、計測して決め直す）
- ステータスバーの件数：表示中のファイルの「変更箇所の数」（連続した変更のまとまりを 1 件）を表示し、クリックでそのファイルを既読にする。表示中のファイルに未読がなければ `未読○ファイル` を表示し、クリックで未読ファイルの一覧を出す。一覧で選んだファイルを開く。未読がまったくないときは `未読なし` と表示する（「ステータスバーの件数」の節を参照）
- 変更前のテキストの見せ方：最初の版は「ホバーでツールチップ表示」と「クリックでその場に展開」の 2 つ。対象は「変更（黄色）」だけ（削除は赤で表示済み）。プレビューに同梱のスクリプトで実現する。変更履歴モードは後回し。変更一覧パネルは作らず、ステータスバーの一覧（QuickPick）を広げて変更箇所に飛べるようにする方向
- 未読ファイルの一覧で選んだファイルは、初期値ではプレビューで開く。そのファイルのプレビューがすでに開いていれば前面に出す。設定 `markdownUnreadChanges.openUnreadFileIn`（`preview` / `editor`）で選べる（2026-11-17 追加）
- 表は行単位で差分を検出し、変わった行（`<tr>`）だけに色を付ける
- 表の扱い：比較の前に空白と区切り行の `-` の数を正規化する。列の増減と配置の変更は、表全体の枠とラベルで示す（「表の差分」の節の提案 1〜3）
- Git は使わない。コミットしなくても、前回既読にした時点との差分が分かること
- VS Code 標準の Markdown プレビューに色を付ける（独自のエディタやビューは作らない）

## やりたいこと
- Claude Code などがノートを書き換えたら、標準の Markdown プレビューで変更箇所に色が付く
  - 黄色：変更
  - 緑：追加
  - 赤：削除（消えた内容が分かる形で表示）
- ステータスバーに「変更○件」と表示する
- ステータスバーをクリックすると既読になり、色が消える
- 変更箇所で、変更前のテキストを確認できる（ホバーのほか、ホバー以外の方法も検討）

## オフライン前提の確認方法
「インターネットに一切接続しない」を、思い込みではなく仕組みで確認するための方法。上から順に、効果が高く手間が少ない。

### 1. 静的チェック（ESLint で通信系の API を禁止する）
- `no-restricted-imports` で次のモジュールの読み込みを禁止する：`http` / `https` / `http2` / `net` / `tls` / `dgram` / `dns` / `child_process`
- `no-restricted-globals` / `no-restricted-properties` で次を禁止する：`fetch` / `XMLHttpRequest` / `WebSocket` / `EventSource` / `navigator.sendBeacon`
- VS Code API で禁止するもの：`vscode.env.createTelemetryLogger`（テレメトリ）、`vscode.env.openExternal`（外部 URL を開く）、`globalState.setKeysForSync`（Settings Sync に載せる）
- 効果：書いた瞬間にエディタ上でエラーになる。C# のアナライザーと同じ感覚

### 2. 依存パッケージを増やさない
- 実行時の依存（`dependencies`）は原則ゼロにする。例外として追加するのは、ソースを読んで通信しないことを確認したパッケージだけ（確認した版を固定し、理由をこのノートに残す）
- `npm ls --omit=dev` の結果が、空か確認済みのパッケージだけであることを確認する
- 理由：依存ライブラリの中に通信するコードがあると、1 のチェックでは見つけられないため

### 3. 成果物（.vsix）の中身を検査する
- `vsce ls` で、パッケージに含まれるファイルの一覧を確認する
- ビルド後の `dist/extension.js` を、`http://` / `https://` / `fetch(` / `require("http` などで検索する
- `package.json` の `markdown.previewStyles` / `markdown.previewScripts` が、拡張内の相対パスだけを指していることを確認する
- 注意：ライセンスのコメントなどに URL が含まれて誤検知が出るので、許可リストを用意する

### 4. テストで通信を「罠」にかける
- 結合テストの開始時に、`http` / `https` / `net` の接続関数と `fetch` を、呼ばれたら例外を投げる関数に差し替える
- テストが全部通れば、テストで通った処理の範囲では通信していないことになる

### 5. 実機で確認する（リリース前に手動で）
- ネットワークを切った状態で拡張開発ホストを起動し、すべての機能が動くことを確認する（通信に頼っていないことの確認）
- より厳密に確認したい場合：VS Code のテレメトリを切る（`telemetry.telemetryLevel: off`）。この拡張以外を無効にする（`--disable-extensions`）。そのうえで、Windows のリソースモニターなどで拡張ホストのプロセスが通信していないか見る
- 限界：VS Code 本体や標準プレビュー（ノートの外部画像など）の通信と区別しにくい

### 6. CI で自動化し、README に明記する
- 1〜4 を GitHub Actions で毎回実行する（CI 自体はパッケージの取得に通信するが、拡張の動作とは関係ない）
- README に「Privacy」の節を設け、通信しないこと、何をどこに保存するか（`storageUri`）を書く。Marketplace で利用者が判断できるようにするため

## 表の差分

### 標準プレビューで表の各行にソースの行番号が付くか（確認済み）
- **付く。** 表の各行は `<tr class="code-line" data-line="N">` として出力される（N はソースの 0 始まりの行番号）
- 確認方法：手元の VS Code 1.146.0 に同梱されている `markdown-language-features/dist/extension.js` を直接読んだ（2026-11-17）
  - markdown-it の表のルールが、見出し行と本文の各行の `tr_open` に、その行だけを指す `map`（`[行, 行+1]`）を設定している
  - VS Code は、`map` を持つすべてのトークン（inline を除く）に `data-line` と `code-line` クラスを付けている
- 付かないもの：
  - セル（`<th>` / `<td>`）：行番号が付かない。セル単位で色を付けたい場合は、列の位置（何番目のセルか）で特定する必要がある
  - 区切り行（`|---|:---:|`）：対応する HTML 要素がない。この行の変更は、そのままでは色を付ける場所がない
- 注意：`data-line` は VS Code の内部実装で、公式の API ではない。将来の版で変わる可能性があるので、結合テストで確認し続ける

### 提案 1：比較の前に表の行を正規化する
- セル前後の空白、`|` の前後の空白、区切り行の `-` の数は、比較の前にそろえる
- 理由：フォーマッターや AI が列幅をそろえ直すと、全行の空白だけが変わる。正規化しないと、表全体が黄色になる

### 提案 2：列の追加・削除 →「表の構造の変更」として、表全体に印を付ける
- 判定：既読時点と現在で、同じ表の列数が違う場合
- 表示：各行を黄色にするのではなく、表全体を枠で囲み、「列が変更されました」というラベルを付ける
- 理由：列が増減すると、ソース上は全行が変わる。行単位で色を付けると全行が黄色になり、どこが変わったのか分からなくなる
- 削除された列の内容は、「変更前のテキストの見せ方」（別の論点）で確認できるようにする
- 発展案（後回し）：見出しの名前で列を対応づけ、列の増減以外にも内容が変わったセルや行を個別に色付けする

### 提案 3：区切り行だけの変更
- 空白や `-` の数だけの変更：正規化で吸収し、変更として扱わない（提案 1）
- 配置（`:---` / `:---:` / `---:`）の変更：見た目が変わるので変更として扱う。提案 2 と同じく、表全体の枠と「配置が変更されました」のラベルで示す
- 理由：区切り行には色を付ける要素がない。見出し行を黄色にすると、見出しの文字が変わったと誤解されるため

## 大規模フォルダ対策
目標：1 万ファイル級のフォルダを開いても、VS Code の起動や操作が重くならないこと。

### 提案 1：追跡対象を指定する設定
| 設定 | 初期値 | 内容 |
|---|---|---|
| `markdownUnreadChanges.include` | `["**/*.md"]` | 追跡するファイルの glob。`docs/**/*.md` のように、含めるフォルダを絞れる |
| `markdownUnreadChanges.exclude` | `node_modules` / `.git` / `dist` / `out` / `build` / `vendor` など | 除外する glob。VS Code 標準の `files.exclude` に指定されたものも除外する |
| `markdownUnreadChanges.maxFiles` | 2000 | 追跡するファイル数の上限 |
| `markdownUnreadChanges.maxFileSize` | 1 MB | これより大きいファイルは追跡しない（巨大なログなどを .md で置いている場合の対策） |

- 初期値の 2000 と 1 MB は仮の値。実装後に計測して決め直す

### 提案 2：上限を超えたときの動き
- 全件の取り込みはしない。先頭から 2000 件だけ取り込む方法は、どのファイルが対象になるか利用者に分からないので採用しない
- 代わりに「開いたファイルだけ追跡するモード」に切り替え、通知で `include` の設定を勧める（通知はローカルだけで完結する）
- ステータスバーにも、上限を超えて縮退中であることを表示する

### 提案 3：重くしないための実装方針
- 起動のタイミング：`onStartupFinished`（VS Code の起動が終わってから動く）を使う。`workspaceContains:**/*.md` は起動時に全ファイルを走査するので使わない
- 初回の取り込み：数十件ずつに分けてバックグラウンドで処理し、ステータスバーに進み具合を表示する
- 変更の検知：ファイル監視（`createFileSystemWatcher`）は対象の glob だけに絞る。VS Code を閉じている間の変更は、次に起動したときに、更新日時とサイズを比べて検知する（違うものだけ中身を比べる）
- 差分の計算：変更を検知したファイルだけ、その時点で計算して結果をキャッシュする。ほかのファイルは計算しない
- スナップショット：1 ファイルにつき 1 つのファイルとして `storageUri` に保存し、必要になったときだけ読み込む（全件をメモリに載せない）

## ステータスバーの件数

### 数える単位（確定：変更箇所の数）
- 推奨：**変更箇所の数**。連続して変わったブロックのまとまりを 1 件と数える
  - 例：段落を 3 つ続けて書き換えた場合は 1 件、離れた 2 か所を書き換えた場合は 2 件
  - 理由：利用者が「何か所見ればいいか」と一致する。表の 10 行が変わった場合も 1 件になり、件数がふくらみすぎない
- 別案：色の付いたブロックの数（上の例なら 3 件）。画面に見える色の数とは一致するが、表や長いリストで件数がふくらむ
- ツールチップには内訳（変更○・追加○・削除○）を表示する

### 何を対象に数えるか（確定）
| 状況 | 表示 | クリックしたとき |
|---|---|---|
| 未読の .md を表示中 | `変更 3件`（このファイルの件数） | このファイルを既読にする |
| 未読のない .md を表示中、ほかに未読のファイルがある | `未読 2ファイル` | 未読のファイルの一覧（QuickPick）を開く。選んだファイルを開く（確定） |
| .md 以外を表示中 | `未読 2ファイル` | 同上 |
| 未読がまったくない | `未読なし`（確定） | なし |

- 推奨：クリックで既読にするのは「表示中のファイル」だけにする。ワークスペース全体を一度に既読にすると、見ていないファイルの変更まで消えてしまうため
- 全体をまとめて既読にしたい場合は、コマンドパレットのコマンド（確認ダイアログ付き）で別に用意する
- ツールチップに、ほかに未読のファイルが何件あるかも表示する
- 未読のファイルの一覧は、「変更前のテキストの見せ方」の論点にある「変更一覧パネル」と関係するので、そこで改めて決める

## 実装メモ（2026-11-17 初日）

### 実装の途中で分かったこと（設計に影響あり）
- 標準プレビューは、トークン化の結果を文書ごとにキャッシュし、トークン化の時点では `env.currentDocument` が空（手元の VS Code 1.146.0 の `markdown-language-features` を読んで確認）
  - そのため、markdown-it の core ルールでは「どのファイルを描画しているか」が分からない
  - 対応：`md.renderer.render` を包み、描画の時点で `env.currentDocument` を見て色付けする。キャッシュされたトークンは書き換えず、色付けしたトークン列を新しく作る（テストで確認）
  - 既読にしたときは `markdown.preview.refresh` でプレビューを描き直す
- 段落の色付けは `<div class="muc-block ...">` で包む方式にした。リストの中の段落（tight list）は `<p>` が出力されず、属性を付けられないため。表の行だけは `<tr>` に直接クラスを付ける

### 不具合の記録：書き換えていないファイルが未読一覧に出る（2026-11-17 修正）
- 症状：`ai/claude-md.md` が未読一覧に出るが、プレビューには変更点がない
- 調査の結果：スナップショットは正しく保存されていた（本文とバイト単位で一致）。件数を数える処理と色付けの処理は同じ比較（`computeLineDiff`）を使っており、比較の仕方の違いではなかった。食い違っていたのは `index.json` の未読の記録（`unread: true, count: 1`）だけ。count 1 は「ファイル全体が追加」の件数
- 原因：初回の取り込みの途中に、同じファイルの変更通知が届いた（OneDrive の同期などで、内容が変わらなくても届く）。変更通知の処理が「まだ記録のないファイル＝新しいファイル」と判断して空のスナップショットと比べ、その結果を、取り込みの処理が正しいスナップショットを書いた後で上書きした。さらに起動時の確認は更新日時とサイズが同じなら中身を見ないので、誤った記録が残り続けた
- 修正
  - 同じファイルの処理（取り込み・変更通知・編集・既読）を 1 つずつ順に実行する
  - 取り込み中に届いた変更通知は、取り込みが終わってから処理する
  - 起動時、未読と記録されたファイルは更新日時が同じでも中身を比べ直す（既存の誤った記録もこれで直る）
  - 表示中のファイルで、記録と実際の比較結果が食い違っていたら記録を直す
  - あわせて、改行コード（CR のみも含む）と先頭の BOM の違いを変更として扱わないようにした
- テスト：`test/tracker.test.mts`（`vscode` を偽物に差し替えて Tracker を動かす。修正前のコードで失敗することを確認済み）

### 不具合の記録：プレビューを表示中にステータスバーから既読にできない（2026-11-17 修正）
- 症状：ステータスバーをクリックすると未読一覧（コマンドパレットに似た画面）が出るだけで、既読にならない。コマンドパレットの「Mark Current File as Read」も何も起きない
- 原因：プレビューにフォーカスがあるとき、対象のファイルを「直前にエディタで表示していたファイル」としていた。未読一覧からプレビューで開いたファイルはエディタで表示されないため、対象が不明になり（または別のファイルを指し）、ステータスバーが「未読 ○ファイル」になっていた
- 修正：プレビューのタブの題名（末尾がファイル名）と、追跡しているファイルの名前を照らし合わせて対象を決める（`src/ui/previewTarget.ts`）。同じ名前のファイルが複数あるときは最近開いたものを優先し、それでも決まらなければ対象なしとする（別のファイルを誤って既読にしないため）。対象が分からないときと追跡の対象外のときは、コマンドで理由を通知する
- テスト：`test/previewTarget.test.mts`

### 不具合の記録：最初からプレビューで開く形で「未読 ○ファイル」になる（2026-11-17 修正）
- 症状：`workbench.editorAssociations` で Markdown を最初からプレビューで開く設定（タブの題名がファイル名だけ、右上に「Markdown Preview」）だと、プレビュー表示中でもステータスバーが「未読 ○ファイル」になる
- 原因：この形のプレビューは Webview ではなくカスタムエディタ（`TabInputCustom`、viewType `vscode.markdown.preview.editor`）として開く。プレビューの判定が Webview のタブだけを見ていた
- 修正：カスタムエディタのタブは表示中のファイルの URI を持っているので、題名からの推定ではなく URI で判定する（同じファイル名が複数あっても正確）。未読一覧から開くときに既存のプレビューを探す処理も同様に対応した
- テスト：`test/previewTarget.test.mts` にタブの種類ごとの判定を追加

### 対応の記録：制限モード（信頼していないフォルダ）への対応（2026-11-17）
- `package.json` の `capabilities.untrustedWorkspaces` を `supported: "limited"` にした。未宣言だと、制限モードでは拡張機能ごと無効になり、色付けもステータスバーも動かない
- `restrictedConfigurations` に include / exclude / maxFiles / maxFileSize / openUnreadFileIn を指定した（VS Code 側でもフォルダ側の値を無視する）
- 拡張側でも、制限モードでは `inspect()` のユーザー設定と初期値だけを使う（`src/config.ts` の `readSetting`）。`files.exclude` は VS Code 本体の設定で `restrictedConfigurations` に入れられないため、この処理で無視する
- フォルダを信頼したら（`onDidGrantWorkspaceTrust`）取り込み直す
- 制限モードで Markdown プレビューは CSP が厳格になるが、拡張機能が同梱する previewScripts / previewStyles は読み込まれる想定。実機での確認が必要
- テスト：`test/config.test.mts`
